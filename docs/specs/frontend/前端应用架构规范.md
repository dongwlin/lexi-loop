# 前端应用架构规范

## 1. 适用范围

本规范适用于基于 Vite、TypeScript 的 Vue 单页应用（SPA）。技术选型以《[[前端技术栈]]》为准；项目遵循《[[Vue 最佳实践]]》；交互与无障碍见《[[前端交互与可访问性规范]]》，测试见《[[前端测试规范]]》，HTTP 契约见《[[HTTP API 设计规范]]》，API 调用、token 与会话恢复见《[[前端 API 与认证集成规范]]》。

本规范只规定前端应用的职责、目录和依赖边界，不重复规定：

- HTTP 响应、错误码、分页与字段格式
- Vue 组件语法细节
- 具体颜色、间距和 Design Token
- 缓存时间、虚拟列表等性能参数

项目可以省略暂时用不到的目录，但核心目录名称必须保持一致。

---

## 2. 核心原则

### 2.1 页面统一放在 `pages/`

所有由前端 Router 直接加载的路由页面必须放在 `src/pages/`，文件名以 `Page` 结尾：

```text
pages/auth/LoginPage.vue
pages/task/TaskListPage.vue
pages/task/TaskDetailPage.vue
pages/error/NotFoundPage.vue
```

Vue 项目使用同样的目录和命名，只把扩展名换成 `.vue`。

不得再使用以下目录保存路由页面：

- `routes/`
- `views/`
- `screens/`

`app/router.ts(x)` 保存路由声明，`pages/` 保存页面组件。页面目录的存在不代表自动采用文件路由；默认显式维护路由表。

### 2.2 页面负责编排，Feature 负责业务能力

Page 是路由入口和组合面，负责：

- 读取并校验路由参数和查询参数
- 组合一个或多个 Feature
- 决定页面级 Loading、Empty、Error、Forbidden 和 Success 状态
- 连接页面布局、标题、面包屑和主要操作
- 把可分享、可恢复的页面状态同步到 URL

业务查询、Mutation、表单规则、业务组件和状态转换应放在 `features/`，不要把完整功能实现堆进 Page。

### 2.3 按业务能力组织，不按技术类型平铺

任务、认证、成员等业务代码分别归入 `features/task`、`features/auth`、`features/member`。不要把所有查询放进一个全局 `queries/`，所有表单放进一个全局 `forms/`，所有类型放进一个全局 `types/`。

全局目录只保存真正跨 Feature 的能力。

### 2.4 状态只有一个权威来源

- 服务端数据 → TanStack Query
- 可分享的页面状态 → URL
- 单个组件或页面的瞬时 UI 状态 → 本地 state
- 跨页面且与服务端无关的客户端状态 → Pinia
- 必须跨刷新保存的客户端配置 → 封装后的浏览器存储

不要把 Query 数据复制进 Pinia 或组件 state 再维护第二份。

### 2.5 依赖方向必须向下

高层负责组合低层，低层不得反向引用高层：

```text
main
  ↓
app
  ↓
pages
  ↓
features
  ↓
components / hooks / composables / stores / lib / utils
```

循环依赖说明职责放错了位置，不能通过调整 import 顺序或增加 Barrel File 掩盖。

### 2.6 先保持扁平，再按真实复杂度拆分

目录是为了表达已存在的职责，不是预先猜测未来。只有一个文件时直接放在 Feature 根目录；出现多份同类文件后再建立 `components/`、`api/`、`schemas/` 等子目录。

不要创建空目录，也不要为每个 Feature 机械复制相同的目录模板。

## 3. 标准目录结构

以下是中等规模应用的完整结构。小项目可以省略暂时不用的目录：

│   │   └── TaskDetailPage.vue

## 4. 各目录职责

### 4.1 `app/`：应用装配

`app/` 负责一次性的全局装配：

- 根组件
- Router 与路由守卫
- Query Client
- Vue Router、Pinia、Query 插件安装
- 顶层 Error Boundary / Error Handler
- 全局导航进度和应用启动状态

`app/` 不保存具体业务页面和业务组件。它可以依赖所有下层目录，因为它是组合根。

推荐：

```text
app/
├── App.vue
├── providers.ts
├── router.ts
├── pinia.ts
└── query-client.ts
```

### 4.2 `pages/`：路由页面

一个 Page 对应一个可直接访问的路由页面。Page 名称使用 `XxxPage`，并按业务域分组：

```text
pages/
├── dashboard/DashboardPage.vue
├── task/TaskListPage.vue
├── task/TaskDetailPage.vue
└── settings/ProfileSettingsPage.vue
```

Page 可以：

- 调用 Feature 暴露的 Query、Mutation、Hook 或 Composable
- 组合多个业务组件
- 使用共享布局和 UI 组件
- 读取 Router 的 params、query/search 和 navigation state
- 持有只服务于当前页面的轻量 UI 状态

Page 不应：

- 直接调用 `fetch` 或拼接 API URL
- 定义可复用的业务规则和校验规则
- 保存全局 Store
- 包含多个独立区域的完整内部实现
- 被 Feature、共享组件或 `lib/` 反向 import

一个只包含标题和简单静态内容的页面可以保留为单文件。只有当页面内出现独立职责时才拆出 Feature 或子组件，不使用固定行数作为拆分标准。

### 4.3 `features/`：业务能力

Feature 表达用户能够理解的业务能力，例如：

- `auth`
- `task`
- `workspace`
- `member`
- `report`

Feature 内可以包含：

| 内容 | 示例 |
| --- | --- |
| 业务组件 | `TaskForm`、`TaskFilter`、`MemberPicker` |
| Query | 任务列表、详情、当前用户 |
| Mutation | 创建、编辑、归档、邀请成员 |
| 表单 Schema | 创建任务、登录、筛选条件 |
| Hook / Composable | `useTaskFilters`、`useAuthSession` |
| Feature Store | 只属于该业务能力的客户端状态 |
| Feature 类型 | 表单值、视图模型、组件契约 |

小 Feature 保持扁平：

```text
features/theme/
├── ThemeToggle.vue
└── useTheme.ts
```

复杂后再拆：

```text
features/task/
├── components/
├── api/
├── hooks/
├── schemas/
└── types.ts
```

Feature 之间允许少量、明确的单向依赖，但不得形成循环。若两个 Feature 经常互相引用：

1. 优先由 Page 在上层组合
2. 把真正通用的 UI 或工具下沉到共享目录
3. 若它们本质上是同一业务能力，合并 Feature

不要为了制造隔离就给每个 Feature 创建接口层、事件总线或重复类型。

### 4.4 `components/`：共享组件

`components/ui/` 保存没有业务语义的基础组件：

- Button
- Input
- Dialog
- Select
- Table
- EmptyState
- Spinner

`components/layout/` 保存跨页面布局：

- AppShell
- Sidebar
- Header
- PageContainer

共享组件通过 props、children/slots、callback/emit 表达契约，不直接读取某个 Feature 的 Store、Query 或 API。

只有至少两个 Feature 确实复用，或组件属于明确的设计系统基础设施时，才放进 `components/`。业务组件即使可复用，也优先留在所属 Feature。

组件测试和 Story 与组件放在同一目录，规则见《[[前端测试规范]]》。

### 4.5 `composables/`：跨 Feature 状态逻辑

这里只保存跨 Feature 复用、带状态或生命周期的逻辑，例如：

- `useMediaQuery`
- `useDebouncedValue`
- `useEventListener`
- `useOnlineStatus`

只被一个 Feature 使用的 Hook/Composable 留在该 Feature 内。纯函数放 `utils/`，不要为了命名统一包装成 `useXxx`。

Vue Composable 使用 Composition API 和 TypeScript；涉及共享可变状态时返回 readonly state 与显式 action，避免调用方任意修改内部状态。

### 4.6 `stores/`：跨 Feature 客户端状态

`stores/` 只保存真正跨页面、跨 Feature 的客户端状态，例如：

- 当前主题与用户偏好
- 全局侧栏开关
- 尚未提交且需要跨页面保留的草稿
- 客户端会话恢复过程中的临时状态

服务端返回的用户、任务、列表和详情不放全局 Store，而由 TanStack Query 管理。

Feature 私有 Store 放在对应 Feature。Vue 按需使用 Pinia Setup Store。不要因为项目安装了状态库，就把所有组件状态移入 Store。

Vue Store 的 state/getter 使用 `storeToRefs()` 解构，action 可以直接解构；Store 之间不得在 setup 阶段形成循环读取。

### 4.7 `lib/`：基础设施适配

`lib/` 保存对框架、浏览器或第三方库的薄封装：

- HTTP Client 与统一错误转换
- 自动生成的 API Client
- Query Client 公共配置
- 浏览器存储适配器
- 环境变量读取与校验
- 日志、日期、国际化等第三方集成入口

`lib/` 不包含任务、订单、用户等业务判断，也不 import `features/`、`pages/` 或 `app/`。

### 4.8 `utils/`、`types/`、`assets/` 与 `styles/`

`utils/` 只保存无状态纯函数。`types/` 只保存真正跨 Feature 的公共类型；不要把所有 API DTO、组件 Props 和表单类型集中到一个文件。

`assets/` 保存参与构建的图片、字体和图标。需要原样由服务器提供的文件使用 Vite 项目的 `public/`，不要在代码中通过脆弱的相对字符串引用构建资产。

`styles/main.css` 保存 reset、全局字体、Design Token 和应用级基础样式。组件专属样式与组件共置；Vue 使用 SFC 时优先放在组件的 `<style scoped>`，Tailwind utility 直接写在组件模板。

## 5. 依赖规则

### 5.1 允许的依赖方向

| 目录 | 可以依赖 | 禁止依赖 |
| --- | --- | --- |
| `app` | `pages`、`features`、所有共享目录 | 无下层限制 |
| `pages` | `features`、`components`、共享 Hook/Composable、Store、`lib`、`utils` | `app` |
| `features` | `components`、共享 Hook/Composable、Store、`lib`、`utils`、公共类型 | `pages`、`app` |
| `components` | 框架、样式、`utils`、通用类型 | `features`、`pages`、`app`、业务 API |
| `hooks` / `composables` | `lib`、`utils`、通用类型 | `pages`、具体业务 Feature |
| `stores` | `lib`、`utils`、通用类型 | `pages` |
| `lib` / `utils` | 第三方库和更底层文件 | `features`、`pages`、`app` |

### 5.2 import 约定

- 同一小目录内使用相对路径
- 跨目录使用 `@/` 指向 `src/`
- 不写超过两层的 `../../../` 跨域 import
- 不在每个目录机械创建 `index.ts`
- Barrel File 只用于确实稳定的公共出口，避免隐藏依赖和扩大模块加载图
- 禁止通过循环 import 依赖模块初始化顺序

### 5.3 不强制 Feature 公共接口层

项目内部可以显式 import Feature 文件：

```ts
import { useTaskListQuery } from '@/features/task/api/queries'
```

不要求每个 Feature 通过 `index.ts`、Facade、事件总线或 consumer-defined interface 暴露能力。只有导入路径频繁变化、Feature 被多个入口复用或需要限制公共 API 时，才增加稳定出口。

## 6. Router 与页面

### 6.1 路由声明

路由表统一放在 `app/router.ts`，路由组件统一从 `pages/` 导入：

```text
app/router
  ├── path、name、meta、layout
  └── lazy import → pages/XxxPage
```

路由声明不得散落在 Feature 内，也不根据 `pages/` 文件路径自动生成 URL。所有公开 URL 都必须在路由表中显式可见、可审查。

默认对 Page 做路由级 Lazy Loading。首屏极小页面可以同步加载，但不为每个内部组件单独创建异步边界。

### 6.2 URL 是可分享页面状态的权威来源

以下状态应优先放进 URL query/search params：

- 分页
- 搜索词
- 筛选和排序
- 当前 Tab
- 可直达的详情 ID

以下状态保留在本地：

- Dialog 是否临时打开
- 输入过程中的未提交值
- Hover、焦点和动画状态
- 不需要刷新恢复的临时选择

Page 负责把 Router 的字符串参数解析为明确类型和默认值，再传给 Feature。Feature 不应在深层组件中随意读取全局 Router。

### 6.3 路由守卫

路由守卫只处理进入页面前必须决定的导航问题：

- 是否已经完成会话恢复
- 是否需要登录
- 是否允许访客进入
- 是否存在未保存修改需要确认

普通业务数据由 Page 调用 Feature Query 获取，不要把所有 API 请求塞进全局守卫。前端守卫只改善用户体验，真正的认证与授权必须由后端执行。

守卫必须：

- 明确处理直接访问、刷新、后退和重定向来源
- 避免登录页再次重定向到登录页
- 异步检查必须等待并处理失败
- 保留经过校验的返回地址，登录后恢复原导航
- 对所有分支编写路由测试

### 6.4 Vue Router

- 生产 SPA 使用官方 Vue Router，不手写 Hash Router
- 使用动态 import 从 `pages/` 加载页面
- 路由 meta 描述 `requiresAuth`、layout 等声明式信息
- 守卫使用 return-based 写法，不使用 `next()`
- 在守卫函数内部获取 Pinia Store，避免模块加载时 Pinia 尚未安装
- 同一路由 params/query 变化可能复用 Page 实例；使用响应式 Query Key、`watch` 或 `onBeforeRouteUpdate` 处理，不只依赖 `onMounted`
- `beforeEnter` 不负责同一路由参数变化时的权限检查；这类检查放全局守卫或响应路由更新的位置

## 7. 状态归属

### 7.1 决策顺序

新增状态时按以下顺序判断：

1. 能否由现有 props、state 或 Query 数据派生？能则直接计算
2. 是否只服务一个组件？放组件本地
3. 是否只服务当前页面且需要子组件共享？由 Page/Feature Container 持有并通过 props/context 提供
4. 是否应该通过链接分享、刷新恢复或支持浏览器前进后退？放 URL
5. 是否来自服务器？放 TanStack Query
6. 是否跨页面且完全属于客户端？最后才放 Pinia

### 7.2 Server State

TanStack Query 负责：

- API 请求生命周期
- 缓存、失效和后台更新
- 分页和 Infinite Query
- Mutation 状态
- 乐观更新与回滚

Query Key、Query Function 和 Mutation 放在所属 Feature。Page 只传入明确参数和组合结果，不在页面里手写缓存操作细节。

### 7.3 Client State

客户端 Store 必须保持最小：

- 原始状态作为唯一来源
- 派生状态使用 selector、getter 或 computed
- 修改集中在命名 action
- 不保存可以从 Router 或 Query 推导的数据
- 持久化时包含版本和迁移策略

Store 不应成为组件之间传递数据的默认手段。父子组件仍使用 props 与 callback/emit。

## 8. API 与数据流

API Client、错误模型、跨站请求、token 存储、refresh token 轮换、并发刷新与认证 `401` 重放的具体规则见《[[前端 API 与认证集成规范]]》。本节只规定目录和数据流边界。

### 8.1 分层

```text
Page
  ↓
Feature Query / Mutation
  ↓
Feature API Function
  ↓
lib/api Client
  ↓
HTTP API
```

- `lib/api/client.ts`：Base URL、Header、认证、Abort、统一响应解包和错误转换
- `lib/api/generated/`：OpenAPI 生成的 Client 与 DTO
- `features/<name>/api/`：业务 Query、Mutation、Query Key 和少量 DTO 适配
- `pages/` 与组件：只调用 Feature 暴露的业务数据能力

禁止在 Page、组件、Store 中直接散落 `fetch()`、URL 字符串和响应结构判断。

### 8.2 DTO 与视图类型

API DTO 与页面视图恰好一致时可以直接使用，不为“分层完整”机械复制类型。只有出现以下情况才建立适配：

- 字段需要组合、格式化或重命名
- 一个视图由多个响应组成
- API 可空性不适合组件契约
- 表单值与提交 DTO 不同
- UI 需要判别联合或额外派生状态

生成类型不得手工修改。Feature 类型留在 Feature 内，不把所有 DTO 重新导出到全局 `types/`。

### 8.3 数据流闭环

写操作统一遵循：

```text
用户操作
→ Feature Mutation
→ API Client
→ 成功：精确更新或失效 Query
→ 失败：转换为可展示错误，必要时回滚
→ Page/组件根据 Mutation 状态反馈
```

不要通过全局事件总线广播“数据已变化”。Query Cache 是服务端状态同步的主要协调机制。

## 9. 组件与 Feature 拆分

### 9.1 Page 保持为组合面

Page 可以保留路由解析、页面标题、布局和状态分支，但出现以下任一情况时应拆出 Feature 组件或 Hook/Composable：

- 同时承担数据编排和多个独立 UI 区域
- 表单、筛选、列表、详情等区域有独立行为
- 一段业务行为需要单独测试或 Storybook 展示
- 逻辑被另一个 Page 复用
- 页面因嵌套条件难以一次读懂

不要使用“超过 100 行必须拆分”之类机械阈值；以职责和变化原因判断。

### 9.2 组件契约

展示组件优先接受明确数据并产生明确事件：

```text
Page / Feature Container
  ├── props / slots / children → 展示组件
  └── callback / emit          ← 用户操作
```

共享组件不得直接读取业务 Store 或发业务请求。业务组件可以调用同 Feature 的 Hook/Composable，如果同时承担编排和展示，应拆分为 Container 与 Presentational Component。

### 9.3 Vue

- 使用 Vue 3 Composition API、`<script setup lang="ts">`
- Page 和根组件默认只做组合
- props 向下、emit 向上；`v-model` 只用于真正的双向组件契约
- Feature 逻辑放 Composable，派生值使用 `computed`，watcher 只处理副作用
- provide/inject 只用于深层依赖和上下文，mutation 留在 Provider 或显式 action

---

## 10. 表单

表单属于业务 Feature，而不是共享 `components/ui`：

```text
features/task/
├── components/TaskForm.vue
├── schemas/task-form.ts
├── api/mutations.ts
└── types.ts
```

职责划分：

- UI 控件 → `components/ui`
- 字段组合和交互 → Feature Form
- 客户端 Schema → Feature `schemas/`
- 提交与缓存更新 → Feature Mutation
- 页面关闭、跳转和成功反馈 → Page

客户端校验用于即时反馈，不能替代后端校验。服务端字段错误应映射到对应表单项；非字段错误显示在表单级错误区域。

表单草稿默认保留在组件或 Feature 本地。只有确实需要跨页面恢复时才进入 Store 或持久化存储。

---

## 11. Loading、Empty 与 Error

每个重要 Page 都必须明确处理：

- 首次 Loading
- 有旧缓存时的后台刷新
- Empty
- 可恢复 Error
- Forbidden
- Not Found
- Success

不要用全局 `isLoading` Store 控制所有页面。Query、Mutation、Router 和应用初始化分别拥有自己的状态，Page 根据上下文组合展示。

应用级异常由 `app/` 的 Error Boundary/Error Handler 兜底，路由级错误在对应 Page 边界恢复，Feature 可预期错误由组件就近展示。

## 12. 环境、配置与构建

### 12.1 环境变量

客户端只能读取 `VITE_` 前缀变量。它们会进入浏览器构建产物，因此不得包含密码、数据库连接串、私钥或真正的 Secret。

业务代码不直接到处读取 `import.meta.env`。统一由 `lib/env.ts` 读取、转换并校验，其他模块 import 已类型化的配置。

### 12.2 Vite 配置

`vite.config.ts` 只保存构建工具职责：

- Vue 官方插件
- `@` → `src` Alias
- 本地开发 API Proxy
- 构建与静态资源配置
- 测试和 Storybook 所需插件集成

不要把业务 Feature 开关、权限判断或 API 数据写进 Vite Plugin。Vite 配置统一使用 TypeScript 与 ESM。

### 12.3 资产和部署

- 代码中 import 的资产放 `src/assets/`
- 必须保持固定公开路径、不经过构建转换的文件放 `public/`
- SPA 使用 History 路由时，生产服务器必须把未知前端路径回退到 `index.html`
- Route Page 默认按路由分包，构建失败和 Chunk 加载失败必须进入可恢复错误状态

## 14. 渐进式演进

### 14.1 小项目起点

小型应用可以从以下结构开始：

```text
src/
├── app/
├── pages/
├── components/
├── lib/
└── main.ts
```

出现真实业务能力后再增加 `features/`；出现跨页面客户端状态后再增加 `stores/`；出现跨 Feature 状态逻辑后再增加 `hooks/` 或 `composables/`。

### 14.2 提取信号

| 现象 | 调整 |
| --- | --- |
| Page 包含多个独立业务区域 | 提取 Feature 组件 |
| 两个 Page 复制同一业务逻辑 | 提取到所属 Feature |
| 两个 Feature 复用无业务语义组件 | 下沉到 `components/` |
| 多个 Feature 复用纯函数 | 下沉到 `utils/` |
| 同一 Feature 出现多份 Query/Mutation | 建立 Feature `api/` |
| Store 之间形成循环依赖 | 重新划分所有权或由上层编排 |
| `types/` 成为任意类型堆放处 | 把类型移回 Feature 或组件附近 |

### 14.3 不做预防性抽象

以下做法必须有当前需求支持：

- Feature Facade
- 全局事件总线
- 插件系统
- 自动文件路由
- 微前端
- 每个 Feature 的独立 Service/Repository 接口
- 大量重复的 `index.ts`

“以后可能会用到”不能单独成为引入理由。

---

## 15. 禁止的反模式

- 把路由页面放在 `routes/`、`views/` 或 `screens/`
- Page 直接调用 `fetch`、保存 Query Cache 细节或实现完整复杂表单
- 把所有代码都放进 `components/`
- 把所有 API 数据复制进 Pinia
- 深层业务组件直接读取 Router 形成隐藏依赖
- 共享 UI 组件 import 业务 Feature
- 为了“解耦”使用全局事件总线同步普通 CRUD 数据
- 为每层重复创建相同 DTO 和类型转换
- 使用一个巨大的 `types.ts`、`utils.ts` 或 `api.ts` 承载全项目
- 自动生成目录模板后留下大量空文件和占位接口
- 依赖 Barrel File 隐藏循环依赖
- 在客户端环境变量中保存 Secret

## 16. 速查清单

### 目录

- [ ] 所有 Router 直接加载的页面都在 `pages/`，并以 `Page` 结尾？
- [ ] 路由声明在 `app/`，没有把页面组件放进 `routes/`？
- [ ] 业务代码按 Feature 组织，而不是按技术类型全局平铺？
- [ ] 没有为了完整目录树创建空目录和占位文件？

### 职责

- [ ] Page 负责路由与组合，Feature 负责业务行为？
- [ ] 共享组件不依赖 Feature、Page、Store 或业务 API？
- [ ] `lib/` 不包含业务判断？
- [ ] 纯函数放 `utils/`，有状态逻辑才使用 Hook/Composable？

### 状态

- [ ] Server State 只由 TanStack Query 管理？
- [ ] 可分享和可恢复的筛选、分页、Tab 在 URL 中？
- [ ] Store 只保存跨页面客户端状态？
- [ ] 没有保存可派生的重复状态？

### 数据与路由

- [ ] Page 和组件没有散落的 `fetch` 与 API URL？
- [ ] Query Key、Query 和 Mutation 留在所属 Feature？
- [ ] 路由参数在 Page 边界被解析和校验？
- [ ] 认证守卫不会形成循环重定向，并覆盖直接访问和刷新？

### 质量

- [ ] 重要 Page 覆盖 Loading、Empty、Error、Forbidden 和 Success？
- [ ] 业务组件具有对应测试，复用组件具有 Story？
- [ ] 跨目录依赖方向符合本规范且没有循环？
- [ ] 新抽象解决的是当前重复或复杂度，而不是想象中的未来需求？
