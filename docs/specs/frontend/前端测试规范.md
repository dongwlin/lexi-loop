# 前端测试规范

## 1. 适用范围

本规范适用于基于 Vite、TypeScript 的 Vue Web 应用，统一使用 **Vitest** 作为单元测试、组件测试和页面集成测试的执行器，并使用 **Storybook + Vitest addon** 开发、展示和测试可复用 UI 组件。

本规范解决以下问题：

- 什么行为值得测试
- 单元、组件、页面集成和真实浏览器测试如何分工
- Story、普通测试文件和 E2E 分别承担什么职责
- 如何组织测试文件、查询元素、处理异步行为和测试替身
- Vue 项目如何建立稳定的测试环境
- 覆盖率和 CI 应承担什么职责

端到端测试（E2E）不由 Vitest 取代。需要验证完整部署环境、跨页面主流程或真实后端协作时，统一使用 Playwright；本规范规定它与 Vitest 测试的边界，版本选型见《[前端技术栈](前端技术栈.md)》。

API Client、会话恢复、refresh token 轮换、并发刷新和认证 `401` 请求重放的必测场景见《[前端 API 与认证集成规范](前端%20API%20与认证集成规范.md)》。

组件与页面应满足的语义、键盘、焦点、表单、反馈、动效和 WCAG 2.2 AA 行为见《[前端交互与可访问性规范](前端交互与可访问性规范.md)》；本规范只规定如何测试这些行为。

## 2. 核心原则

### 2.1 测试用户可观察的行为

组件测试应从使用者视角验证：

- 页面展示了什么
- 用户可以执行什么操作
- 操作后界面如何变化
- 请求成功或失败后给出什么反馈
- 组件通过回调或 emit 暴露了什么结果

不要把内部 state、私有方法、Hook/Composable 调用次数和子组件树形结构当成主要断言。只要公共行为没有变化，重构实现不应导致测试大面积失败。

### 2.2 选择最低成本且足够可信的测试层级

能用纯函数单元测试证明的规则，不挂载组件；需要验证 DOM 交互时使用组件测试；只有跨路由、状态管理和 HTTP 边界的行为才使用页面集成测试。

测试层级越高，数量应越少：

| 层级 | 主要对象 | 默认环境 | 速度 |
| --- | --- | --- | --- |
| 单元测试 | 纯函数、校验器、状态转换、Store、简单 Hook/Composable | `node` 或 `jsdom` | 极快 |
| 组件测试 | 表单、列表、弹窗、可复用组件 | `jsdom` | 快 |
| Story 测试 | 可复用组件的视觉状态、交互和可访问性 | Storybook + Vitest Browser Mode | 中等 |
| 页面集成测试 | 路由页面、Query Cache、Store、HTTP 状态组合 | `jsdom` + HTTP mock | 中等 |
| 浏览器组件测试 | 焦点、拖拽、布局、CSS、浏览器原生行为 | Vitest Browser Mode | 较慢 |
| E2E | 部署后的关键用户流程 | Playwright + 真实浏览器与应用 | 最慢 |

### 2.3 测试是风险控制，不是文件配额

不要求每个组件、每个 Hook 或每一行代码都有测试。优先覆盖一旦出错会造成业务损失、权限泄漏、数据错误或高回归成本的行为。

### 2.4 每个测试必须独立且可重复

- 任意测试都能单独运行
- 不依赖测试执行顺序
- 不访问真实公网服务
- 不复用其他测试留下的 DOM、Store、Query Cache、Mock 或定时器
- 时间、随机数、时区和浏览器存储会影响结果时，必须显式控制

## 3. 统一测试栈

### 3.1 通用依赖

| 工具 | 职责 |
| --- | --- |
| Vitest | 测试执行、断言、Mock、Fake Timer、覆盖率 |
| `jsdom` | 默认 DOM 模拟环境 |
| Testing Library | 以用户视角查询 DOM 和触发交互 |
| `@testing-library/user-event` | 模拟点击、输入、键盘等用户操作 |
| `@testing-library/jest-dom` | `toBeVisible`、`toHaveAccessibleName` 等 DOM 断言 |
| Mock Service Worker（MSW） | 在 HTTP 边界模拟 API 成功、失败和延迟 |
| Storybook | 隔离开发和展示组件状态，把 Story 作为可执行 UI 用例 |
| `@storybook/addon-vitest` | 把 Story 转换为 Vitest 真实浏览器组件测试 |
| `@storybook/addon-a11y` | 使用 axe 检查 Story 的常见可访问性问题 |
| `@vitest/coverage-v8` | 覆盖率收集 |
| `@playwright/test` | 从部署应用入口验证关键 E2E 流程 |

### 3.2 Vue

Vue 项目默认使用：

- `@testing-library/vue`：用户视角的组件和页面测试
- `@vue/test-utils`：需要精确验证 props、slots、emit、Teleport 或 Composable 宿主环境时使用
- Vitest

不要仅因为 Vue Test Utils 能访问 `wrapper.vm`，就直接断言组件内部响应式状态或调用内部方法。

## 4. 测试优先级

### 4.1 P0：必须覆盖

- 认证恢复、退出登录和权限判断
- 金额、数量、时间、状态流转等业务规则
- 创建、修改、删除、提交等关键 Mutation
- 表单必填、格式、边界值和服务端字段错误
- Loading、Empty、Error、Success 四类页面状态
- 乐观更新失败后的回滚
- 共享 UI 组件的关键 Story、交互和可访问性检查
- 已修复的生产缺陷或高风险回归问题

### 4.2 P1：按风险覆盖

- 路由参数、查询参数和受保护路由
- Query Key、缓存失效和分页筛选
- Store 的状态转换与持久化恢复
- 可复用复杂组件的键盘和交互行为
- 业务组件的长文本、禁用、只读、危险状态和窄视口 Story
- 防抖、节流、定时刷新和请求取消
- Error Boundary 或全局错误展示

### 4.3 P2：通常不单独测试

- 没有条件分支的纯展示包装组件
- 框架、UI 组件库和 TanStack Query 等第三方库自身的行为
- Tailwind class 的具体排列顺序
- 私有变量、内部函数调用次数和组件内部树形结构
- 仅为了提高覆盖率而执行、却没有有效断言的代码

## 5. 文件组织与命名

测试默认与被测文件相邻；只有跨多个 Feature 的页面集成测试和共享测试设施放在顶层 `tests/`：

```text
src/
├── features/
│   └── task/
│       ├── TaskForm.vue
│       ├── TaskForm.stories.ts
│       └── TaskForm.test.ts
├── lib/
│   ├── money.ts
│   └── money.test.ts
tests/
├── integration/
│   └── task-page.test.ts
├── mocks/
│   ├── handlers.ts
│   └── server.ts
└── setup.ts
```

组件测试使用 `ComponentName.test.ts`，Story 使用 `ComponentName.stories.ts`。统一使用 `.test.*`，不要在同一项目混用 `.spec.*`。

测试名称应描述场景和结果：

```ts
describe('TaskForm', () => {
  test('标题为空时阻止提交并显示字段错误', async () => {
    // ...
  })
})
```

避免使用没有行为信息的名称，如“works”“renders correctly”“test submit”。

一个测试只表达一个业务行为，可以包含为证明该行为所需的多个相关断言。测试正文按 Arrange、Act、Assert 顺序组织；代码足够清晰时不必机械添加三段注释。

## 6. 元素查询与断言

### 6.1 查询优先级

按照用户和无障碍树能够感知元素的方式查询：

1. `getByRole(..., { name })`
2. `getByLabelText(...)`
3. `getByPlaceholderText(...)`
4. `getByText(...)`
5. `getByTestId(...)`

能通过语义角色、可访问名称或表单标签定位时，不添加 `data-testid`。只有以下情况可以使用 `data-testid`：

- 元素没有合适的语义角色或可见文本
- 同类动态元素需要稳定且唯一的定位符
- 画布、拖拽区域等结构无法通过普通语义表达

`data-testid` 应描述业务语义，如 `task-row-42`，不要使用 `blue-button`、`second-div` 等视觉或结构名称。

### 6.2 断言最终结果

优先断言：

- 用户看见的文本和状态
- 元素是否可见、可用、被选中或拥有正确的可访问名称
- 表单错误是否靠近对应字段
- URL、焦点或页面状态是否发生预期变化
- 对外回调或 Vue emit 是否携带正确数据

不要仅断言“某函数被调用”，除非调用外部端口本身就是被测对象的公共职责。能断言最终 UI 结果时，应以最终结果为准。

使用 `getBy*` 断言元素必须存在，使用 `queryBy*` 断言元素不存在，使用 `findBy*` 等待异步出现。不要用 `queryBy*` 代替所有查询来掩盖错误信息。

## 7. 用户交互与异步行为

### 7.1 Vue

- Testing Library 的用户操作必须 `await`
- Vue Test Utils 的 `trigger()` 和 `setValue()` 必须 `await`
- 外部 Promise 或 API 完成使用 `flushPromises()`
- 直接修改响应式值后等待 DOM 更新才使用 `nextTick()`

`nextTick()` 只能等待 Vue 的 DOM 刷新，不能代替等待 HTTP Promise。

### 7.2 定时器与时间

只有防抖、节流、轮询、超时等行为才使用 Fake Timer：

```ts
beforeEach(() => {
  vi.useFakeTimers()
})

afterEach(() => {
  vi.useRealTimers()
})
```

涉及 Promise 的定时任务使用异步推进 API。测试结束前恢复真实定时器，不得让 Fake Timer 泄漏到其他测试。

## 8. 测试替身与 HTTP Mock

### 8.1 Mock 外部边界，不 Mock 被测实现

| 边界 | 推荐方式 |
| --- | --- |
| HTTP API | MSW 拦截真实请求 |
| 时间 | `vi.setSystemTime()` / Fake Timer |
| 随机数、UUID | 注入函数或 `vi.spyOn()` |
| 浏览器 API | `vi.stubGlobal()` 或窄适配器 |
| 环境变量 | `vi.stubEnv()` |
| 邮件、支付、地图等 SDK | 在项目封装层提供 fake/stub |
| Store、Router、Query Client | 每个测试创建全新实例；页面集成测试使用真实实现 |

页面集成测试不得直接 Mock TanStack Query Hook、API Client 返回值或组件内部模块。应让生产请求链路真实执行到 HTTP 边界，再由 MSW 返回符合《[HTTP API 设计规范](../backend/HTTP%20API%20设计规范.md)》的响应；认证端点同时遵循《[前端 API 与认证集成规范](前端%20API%20与认证集成规范.md)》的 token pair 与轮换语义。

这可以同时验证：

- 请求是否真的发出
- 路径、方法和参数是否正确
- API Client 是否正确解包响应与转换错误
- Query 和组件能否共同处理成功、失败和延迟

### 8.2 Module Mock 是最后手段

`vi.mock()` 适合无法通过 HTTP 或依赖注入隔离的模块级外部副作用，不应成为默认测试方法。大量 Mock 项目内部模块通常意味着测试与实现耦合过深。

使用 `vi.mock()` 时必须注意它会提升到 import 之前；需要运行时动态 Mock 才使用 `vi.doMock()`。

### 8.3 测试清理

统一配置自动清理 Mock 和 Spy，并在测试结束后恢复：

- 被修改的全局对象
- 环境变量
- Fake Timer 和系统时间
- `document.body` 中手动挂载的节点
- MSW Handler 覆盖
- Vue App、Teleport 和订阅

不要使用 `retry` 掩盖不稳定测试。测试偶发失败时，应修复未等待的异步行为、共享状态或非确定性输入。

## 9. Vue 专项约定

### 9.1 组件测试

- 默认使用 Testing Library 验证用户行为
- 需要验证组件公共 API 时，可以使用 Vue Test Utils 检查 props、slots 和 emit
- 不直接读取或修改 `wrapper.vm` 中的内部状态
- 默认挂载真实子组件；只有昂贵外部边界或与本用例无关的复杂组件才 stub

### 9.2 Composable

只使用 `ref`、`computed` 等响应式 API 的简单 Composable 可以直接调用测试。使用以下能力时，必须挂载宿主组件：

- `onMounted` / `onUnmounted`
- `provide` / `inject`
- Router 或 Pinia
- 依赖组件实例的 API

宿主组件必须在测试结束后卸载，以验证清理行为并防止订阅泄漏。

### 9.3 TanStack Query

每个测试创建独立 Query Client，并默认关闭 Query/Mutation 重试。页面集成测试至少覆盖：

- 首次加载
- 请求失败
- Mutation 成功后的精确缓存失效或更新
- 乐观更新失败后的回滚

不要把 Query Cache 做成跨测试单例，也不要通过清理全局单例来补救错误的测试结构。

### 9.4 Pinia

- Store 单元测试：每个用例执行 `setActivePinia(createPinia())`，测试真实 Action
- 组件隔离测试：使用 `createTestingPinia()`，默认 stub Action
- 页面集成测试：使用真实 Pinia 和真实 Action，只在 HTTP 边界 Mock
- 需要组件实际执行 Action 时，显式设置 `stubActions: false`

### 9.5 Teleport

单元测试可以 stub Teleport，让内容保留在组件树中；需要验证弹窗真实挂载位置、焦点和交互时，应挂载到 `document.body` 或使用 Browser Mode，并在结束后卸载和清理 DOM。

## 10. Storybook 组件测试

### 10.1 Storybook 的职责

Story 是组件在一个确定场景下的可执行示例，同时承担三项职责：

- 展示组件的主要视觉和交互状态
- 为设计、开发和评审提供独立运行环境
- 通过 Vitest addon 执行渲染、交互和可访问性测试

Storybook 不负责：

- 测试纯函数、Store、Hook 或 Composable 的全部边界分支
- 验证完整页面路由、认证恢复和复杂 Query Cache 协作
- 替代部署环境中的 E2E
- 在没有视觉测试服务时自动完成像素级视觉回归

### 10.2 哪些组件必须编写 Story

以下组件必须有 Story：

- `components/ui` 中对外复用的基础组件
- 表单控件、Dialog、Popover、Menu、Tabs、Toast 等交互组件
- 一个以上 Feature 使用的业务组件
- 拥有 Loading、Empty、Error、Disabled、Selected 等重要状态的组件
- 依赖键盘、焦点、拖拽或响应式布局的复杂组件

以下内容通常不单独编写 Story：

- 只负责拼装页面的路由组件
- 没有独立 UI 契约的一次性包装组件
- 纯 Provider、数据加载器和不可见基础设施
- 已经由上层 Story 完整表达、且没有独立行为的内部碎片

### 10.3 Story 状态设计

每个 Story 只表达一个有意义的状态，名称使用业务语言。根据组件能力选择：

- `Default`
- `Loading`
- `Empty`
- `Error`
- `Disabled`
- `ReadOnly`
- `Selected`
- `LongContent`
- `ManyItems`
- `NarrowViewport`
- `DarkTheme`

不要机械生成所有 props 的笛卡尔积。只有会影响布局、可访问性、用户决策或业务行为的组合才值得成为独立 Story。

Story 必须确定、可重复：不访问真实公网 API，不依赖当前时间和随机值，不复用上一个 Story 留下的 Store 或缓存。需要数据请求时使用 Storybook 的 MSW 集成，并复用与页面集成测试一致的 Handler 工厂。

### 10.4 Interaction Test

可复用组件的一段核心交互优先写在 Story 的 `play` 函数中，使它可以在 Storybook Interactions 面板逐步调试，并由 Vitest addon 在真实浏览器中执行。

示例：

```ts
import type { Meta, StoryObj } from '@storybook/vue3-vite'
import { expect, fn } from 'storybook/test'

import LoginForm from './LoginForm.vue'

const meta = {
  component: LoginForm,
  args: {
    onSubmit: fn(),
  },
} satisfies Meta<typeof LoginForm>

export default meta
type Story = StoryObj<typeof meta>

export const ValidSubmit: Story = {
  play: async ({ args, canvas, userEvent }) => {
    await userEvent.type(canvas.getByLabelText('邮箱'), 'user@example.com')
    await userEvent.type(canvas.getByLabelText('密码'), 'correct-password')
    await userEvent.click(canvas.getByRole('button', { name: '登录' }))

    await expect(args.onSubmit).toHaveBeenCalledWith({
      email: 'user@example.com',
      password: 'correct-password',
    })
  },
}
```

`play` 中的用户操作和 `expect` 都必须 `await`，保证步骤能被 Interactions 面板正确记录和调试。

不要在 `.test.ts(x)` 和 Story `play` 中重复同一个组件行为：

- 组件的代表性视觉状态和主要交互 → Story
- 大量边界组合、纯逻辑和错误映射 → 普通 Vitest 测试
- Router、Store、Query 与 HTTP 共同参与的流程 → 页面集成测试
- 跨页面且依赖真实部署环境的主流程 → E2E

### 10.5 可访问性

验收目标以《[前端交互与可访问性规范](前端交互与可访问性规范.md)》为准。

统一安装 `@storybook/addon-a11y`。新建的共享 UI 和关键交互 Story 应设置 `parameters.a11y.test = 'error'`，让违规在本地与 CI 中导致测试失败。

- `'error'`：正常组件的默认要求
- `'todo'`：仅用于已登记、准备后续修复的存量问题
- `'off'`：仅用于故意展示反例或确实不适用的 Story

不得为了让 CI 通过而随意关闭规则。自动化 axe 检查只能发现部分问题，不能替代键盘操作、焦点顺序、屏幕阅读器语义和人工体验检查。

### 10.6 Provider 与 Decorator

全局 Theme、字体和基础样式在 `.storybook/preview.ts` 统一安装。Router、Query Client、Pinia、Auth 等环境通过 Decorator 提供，但每个 Story 必须获得独立状态。

Preview 导入包含 Tailwind CSS 与 `@radix-ui/colors` 的主样式入口即可。

Decorator 只负责还原必要运行环境，不得隐藏业务数据准备或让 Story 依赖全局可变单例。某个 Story 独有的输入应写在 `args`、`parameters` 或该 Story 的 Handler 中。

### 10.7 Vitest addon

Vite 项目统一使用 `@storybook/addon-vitest`，不再使用基于 Jest 的旧 Storybook test-runner。通过 Storybook CLI 安装 addon，让它创建独立的 `storybook` Vitest Project 和 Browser Mode 配置；不要手抄与当前版本不匹配的底层插件配置。

Story 测试在真实浏览器中运行，但不要求测试前启动或发布 Storybook。Storybook UI 用于本地查看和调试，Vitest CLI 用于自动化执行。

## 11. 页面集成测试

页面集成测试使用真实的 Router、Store、Query Client、表单逻辑和组件组合，只在 HTTP 边界使用 MSW。它验证的是“页面能否完成一段业务行为”，而不是单个函数。

关键页面至少考虑以下状态矩阵：

| 状态 | 验证内容 |
| --- | --- |
| Loading | 有稳定反馈，不误显示空状态 |
| Empty | 说明当前没有数据，并给出合理下一步 |
| Error | 展示可理解的错误，允许重试或恢复 |
| Success | 正确展示数据和可用操作 |
| Forbidden | 不暴露无权限操作，正确处理 `403` |
| Validation Error | 服务端字段错误映射到对应表单项 |

页面集成测试适合覆盖登录、关键表单、列表筛选、详情修改和危险操作确认。不同页面重复验证同一基础 Button、Dialog 或 API Client 行为没有价值。

---

## 12. Browser Mode 的使用边界

`jsdom` 模拟 DOM，但不会提供真实布局和完整浏览器行为。以下情况使用 Vitest Browser Mode：

- 真实 focus / blur 和 Tab 顺序
- Drag and Drop
- ResizeObserver、元素尺寸和视口相关行为
- CSS 计算样式、动画和过渡
- 浏览器原生 Cookie 或事件行为
- 在模拟 DOM 中无法可靠复现的交互缺陷

不要为了“更真实”把所有组件测试迁移到 Browser Mode。普通文本、表单校验、点击和状态变化仍以快速的 `jsdom` 测试为主。

共享 UI 组件优先通过 Storybook Vitest addon 使用 Browser Mode；不适合写成 Story 的页面片段或浏览器 API 适配器，才建立独立 Browser Test。

Vitest Browser Mode 仍属于组件或页面集成测试，不等于从首页访问部署应用的 E2E 测试。

---

## 13. Snapshot

Snapshot 不能作为组件行为的唯一断言。

仅在以下场景谨慎使用：

- 小而稳定的生成结果
- 复杂 SVG 或序列化结构
- 在行为断言之外补充结构回归检查

禁止：

- 对整个页面生成数百行 Snapshot
- 用 Snapshot 代替表单、交互和可访问性断言
- 未审阅差异就批量更新 Snapshot
- 对时间、随机值或频繁变化内容生成 Snapshot

---

## 14. 覆盖率

覆盖率是发现遗漏分支的信号，不是测试质量本身。全局百分比不能证明关键业务已经被正确测试。

统一使用 V8 Coverage，并显式设置 `coverage.include`，避免报告只统计测试已经加载的文件。通常排除：

- `.d.ts`
- 测试文件和测试设施
- 自动生成的 API Client、类型或路由文件
- 纯配置入口

覆盖率要求：

- 新增或修改的核心业务行为必须有对应测试
- 缺陷修复必须先增加能复现问题的回归测试
- 优先查看分支覆盖，确认错误和边界路径是否遗漏
- 项目稳定后可以把当前覆盖率设为基线并只允许提高，不制定脱离风险的统一 `80%` 指标
- 不得为了提高数字编写无断言测试，或随意用 ignore 排除难测代码

Story 测试可以计入 Vitest 覆盖率，但“Story 能渲染”不等于组件行为已充分验证。覆盖率报告应综合普通测试与 Story 测试查看，不能用大量无交互 Story 冲高数字。

## 15. 推荐配置

测试配置放在独立的 `vitest.config.ts`，并与 `vite.config.ts` 合并，以复用框架插件、路径别名和转换配置：

```ts
import { defineConfig, mergeConfig } from 'vitest/config'

import viteConfig from './vite.config'

export default mergeConfig(
  viteConfig,
  defineConfig({
    test: {
      environment: 'jsdom',
      setupFiles: ['./tests/setup.ts'],
      include: [
        'src/**/*.test.{ts,tsx}',
        'tests/**/*.test.{ts,tsx}',
      ],
      clearMocks: true,
      restoreMocks: true,
      unstubEnvs: true,
      unstubGlobals: true,
      retry: 0,
      coverage: {
        provider: 'v8',
        reporter: ['text', 'html'],
        include: ['src/**/*.{ts,tsx,vue}'],
        exclude: [
          'src/**/*.d.ts',
          'src/**/*.test.{ts,tsx}',
          'src/**/generated/**',
        ],
      },
    },
  }),
)
```

默认不启用全局测试 API，测试文件显式从 `vitest` 导入 `describe`、`test`、`expect` 和 `vi`，让依赖来源清楚并减少类型配置。

`tests/setup.ts` 至少安装 DOM Matcher，并负责 MSW 生命周期和通用清理：

```ts
import '@testing-library/jest-dom/vitest'
```

Storybook Vitest addon 负责创建标准的 `storybook` Browser Project。除它以外，只有不适合写成 Story、又确实依赖真实浏览器能力的测试才新增 Browser Project。

安装 Storybook 后，通过 Storybook CLI 添加 `@storybook/addon-vitest` 和 `@storybook/addon-a11y`。Vitest addon 应建立独立的 `storybook` Project；普通单元和 `jsdom` 组件测试保持独立，便于分别执行和定位失败。安装时同时安装 Playwright Chromium 浏览器文件，CI 环境也必须提供对应浏览器依赖。

## 16. 命令与 CI

建议统一脚本：

```json
{
  "scripts": {
    "test": "vitest",
    "test:run": "vitest run",
    "test:coverage": "vitest run --coverage",
    "test:storybook": "vitest --project=storybook",
    "test:e2e": "playwright test",
    "storybook": "storybook dev -p 6006",
    "storybook:build": "storybook build"
  }
}
```

| 命令 | 用途 |
| --- | --- |
| `pnpm test` | 本地 Watch Mode |
| `pnpm test:run` | 单次运行全部 Vitest 测试 |
| `pnpm test:coverage` | 生成覆盖率报告 |
| `pnpm test:storybook --run` | 单独运行 Storybook Vitest Project |
| `pnpm test:e2e` | 在部署或本地预览应用上运行 Playwright E2E |
| `pnpm storybook` | 启动 Storybook UI |
| `pnpm storybook:build` | 验证并构建静态 Storybook |
| `pnpm vitest related <files> --run` | 只运行与指定改动相关的测试 |
| `pnpm vitest <file> -t '<name>'` | 调试指定文件或用例 |

CI 必须运行：

1. TypeScript 类型检查（`tsc` 或 `vue-tsc`）
2. `vitest run`，包含普通测试与 Storybook Project
3. Storybook 静态构建
4. 生产构建

Playwright E2E 至少在主分支、发布候选或具备稳定部署环境的合并请求中运行。认证、核心写操作和高风险回归流程应纳入必跑集合。

覆盖率报告可以在 CI 生成，但不应在没有合理基线时用任意百分比阻断提交。Vitest 类型测试只用于需要稳定公共类型契约的库代码，不能替代应用常规的 `tsc` / `vue-tsc` 检查。

提交代码前不得保留 `.only`；`.skip` 必须说明暂时跳过的外部原因和恢复条件，不允许用它隐藏失败测试。

## 17. 开发工作流

新增业务行为或修复缺陷时，推荐遵循红 → 绿 → 重构：

1. 写一个描述预期行为且当前会失败的测试
2. 用最小实现让测试通过
3. 在测试保护下重构
4. 补齐关键失败和边界场景
5. 组件形成独立 UI 契约时同步补充或更新 Story

纯视觉调整或无行为变化的静态文案不强制先写测试。不要为了形式上的 TDD 制造低价值测试。

## 18. 速查清单

### 测试内容

- [ ] 测试的是用户可观察行为，而不是内部实现？
- [ ] 关键正常、失败和边界路径都已覆盖？
- [ ] 缺陷修复包含能复现原问题的回归测试？
- [ ] 测试层级是否足够低且仍能提供可信结果？

### 组件与交互

- [ ] 优先使用 Role、Label 和可访问名称查询元素？
- [ ] 所有用户操作和异步 DOM 更新都已等待？
- [ ] 没有使用任意时长的延迟解决竞态？
- [ ] Snapshot 不是唯一断言？

### Storybook

- [ ] 共享或复杂 UI 组件具有代表性 Story？
- [ ] Story 覆盖了真正重要的视觉和交互状态，而不是 props 笛卡尔积？
- [ ] 主要交互通过 `play` 在真实浏览器中通过？
- [ ] 新 Story 的 a11y 违规会导致测试失败？
- [ ] Story 不访问真实公网服务，也不依赖全局可变状态？
- [ ] 普通测试与 Story 没有重复验证同一个行为？

### 隔离

- [ ] 每个测试拥有独立 Store、Router 和 Query Client？
- [ ] HTTP 行为在网络边界由 MSW 模拟？
- [ ] Fake Timer、全局对象、环境变量和 DOM 已恢复？
- [ ] 测试可以单独运行且不依赖顺序？

### 提交前

- [ ] `vitest run` 通过？
- [ ] TypeScript 类型检查通过？
- [ ] 受影响的关键流程已通过 Playwright E2E？
- [ ] 没有遗留 `.only` 或无说明的 `.skip`？
- [ ] 没有为追求覆盖率加入无价值断言？
