# 前端技术栈

## 1. 适用范围

本文是 Vite + TypeScript 前端应用的技术选型权威清单，适用于 Vue 单页应用（SPA）。目录与依赖边界见《[[前端应用架构规范]]》，框架写法见《[[Vue 最佳实践]]》，测试与 API 集成分别见《[[前端测试规范]]》和《[[前端 API 与认证集成规范]]》；本文不重复这些规范的实现细节。

默认交付形态是客户端渲染 SPA。SSR、SSG、Next.js 和 Nuxt 不属于默认栈；只有搜索引擎收录、首屏渲染或服务端路由确有要求时，才单独立项选型。

---

## 2. 选型原则

### 2.1 一个问题只保留一个默认答案

同一项目不得同时引入职责重叠的方案，例如：

- Vue Router 与另一套路由器并存
- TanStack Query 与 Store 各自保存同一份服务端数据
- `fetch` Client 与 Axios 并存
- Tailwind CSS 与另一套全量样式框架并存
- Reka UI 与另一套 Vue 组件系统同时提供同类组件
- Vitest 与 Jest 并存

替换默认技术必须说明当前方案无法满足的具体约束，并用 ADR 记录收益、迁移成本和退出方案。个人偏好不是引入第二套方案的理由。

### 2.2 依赖分为基线、框架和按需三类

- **共享基线**：每个项目统一使用，如 TypeScript、Vite、pnpm、TanStack Query 和测试设施
- **框架依赖**：Vue 3
- **按需依赖**：只有出现真实需求时安装，如 Store、表单库、i18n、PWA 和监控 SDK

项目不得为了“以后可能用到”预装按需依赖。

### 2.3 稳定版本优先

新项目使用本规范基线对应的稳定大版本；已有项目不因小版本发布立即追新。大版本升级应作为独立任务完成类型检查、单元与组件测试、Storybook 构建、生产构建和关键 E2E 验证。

依赖版本和 pnpm 版本必须由仓库文件锁定，CI 不使用浮动的 `latest`。

| 领域 | 默认选择 | 说明 |
| --- | --- | --- |
| UI 框架 | Vue 3 | Composition API + `<script setup lang="ts">` |

| 组件测试 | `@testing-library/vue` | 需要精确控制时补充 Vue Test Utils |

## 4. 运行时与包管理

### 4.1 Node.js

项目统一以 Node.js 24 LTS 为本地和 CI 基线。必须在仓库中使用一种机制声明版本，例如 `.node-version`、Volta 或项目现有的版本管理文件；不要同时维护多个互相冲突的 Node 版本来源。

浏览器运行时能力由项目的目标浏览器范围决定，不能因为 Node.js 支持某个 API 就假设目标浏览器也支持。需要 Polyfill 时按实际兼容性数据引入，不全局注入未知用途的 Polyfill 集合。

### 4.2 pnpm

项目只提交 `pnpm-lock.yaml`，不得同时提交 `package-lock.json`、`yarn.lock` 或 Bun Lockfile。`package.json` 使用精确的 `packageManager` 字段锁定 pnpm 版本：

```json
{
  "packageManager": "pnpm@11.0.0"
}
```

示例中的 Patch 版本应替换为项目实际验证过的版本。CI 使用 Corepack 或等价机制读取该字段，并以 Frozen Lockfile 安装；Lockfile 与 `package.json` 不一致时直接失败。

pnpm 的项目设置写在 `pnpm-workspace.yaml`，`.npmrc` 只保留 Registry、认证和确实只能放在其中的 npm 配置。直接 import 的包必须声明为直接依赖，不依赖幽灵依赖或提升后的目录结构。

pnpm 12 属于新的实现世代，在项目的 Node、CI、Workspace、Patch 和构建脚本策略全部验证前，不自动替换本规范的 pnpm 11 基线。

## 5. TypeScript 与 Vite

### 5.1 TypeScript

业务源码、Vite 配置和测试默认使用 TypeScript，开启 `strict`。新增代码不得用 `any`、非空断言或类型强制转换跳过边界建模；确实无法确定的数据先用 `unknown`，经 Zod 或类型守卫收窄后再使用。

推荐基线：

```json
{
  "compilerOptions": {
    "strict": true,
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "noEmit": true,
    "noUncheckedIndexedAccess": true,
    "verbatimModuleSyntax": true
  }
}
```

`target`、`lib` 和框架类型由目标浏览器及 Vite 模板补齐。旧项目升级到 TypeScript 6 时应删除已弃用的旧配置，不通过兼容开关无限期保留历史行为。

### 5.2 Vite

统一使用 Vite 8 和 ESM 配置：

- 配置文件使用 `vite.config.ts`
- Vue 使用 `@vitejs/plugin-vue`
- Tailwind CSS v4 使用 `@tailwindcss/vite`
- 环境变量只通过 `import.meta.env` 和 `lib/env.ts` 的校验层访问
- 只有允许暴露给浏览器的变量才使用 `VITE_` 前缀
- 不在客户端环境变量中保存密码、私钥、refresh token 或服务端 Secret
- 路径别名保持少量且稳定，不为每一层目录创建别名

生产构建输出是不可变静态资源。运行时 API 地址需要按部署环境变化时，使用受控的运行时配置入口，不通过重新解释任意全局变量绕过校验。

## 6. 框架与路由

### 6.1 Vue

Vue 项目使用 Vue 3 Composition API、Single-File Component 和 `<script setup lang="ts">`，不新增 Options API 页面。Router 使用 Vue Router 4，路由页面统一放在 `src/pages/`，路由声明放在 `src/app/router.ts`。

跨组件逻辑优先提取为 Composable；Composable 使用 `use` 前缀、接收响应式输入时兼容 Ref/Getter，并在 `onScopeDispose` 清理副作用。Pinia 不是普通 Composable 的替代品。

### 6.2 路由只管理导航状态

Router 负责 URL、页面匹配、导航守卫、路由参数和页面级代码分割。TanStack Query 负责远端数据；Store 负责跨页面客户端状态。不得把大量 API 缓存放进 Router Loader 的私有状态，也不得用 Store 复制 Query Cache。

可分享和可恢复的筛选、分页、排序与 Tab 状态应放在 URL；弹窗开关、输入焦点等短暂状态留在组件本地。

## 7. API、数据与状态

### 7.1 HTTP Client

默认使用浏览器原生 `fetch`，在 `src/lib/api/client.ts` 建立唯一薄封装，统一处理：

- API Base URL 和超时
- `Authorization: Bearer` 注入
- AbortSignal 与请求取消
- 响应解析和应用错误映射
- refresh token 轮换、并发刷新协调与认证 `401` 重放
- 可观测性所需的请求 ID 和安全日志

具体认证行为以《[[前端 API 与认证集成规范]]》为准。默认不引入 Axios；仅当项目依赖其无法用标准 `fetch` 合理满足的能力时，才允许通过 ADR 替换整个 Client，而不是并存。

### 7.2 API 代码生成

后端以 Swagger 2.0 / OpenAPI 文档提供契约，前端默认使用 Orval 生成 TypeScript 类型和请求函数。生成物放在 `src/lib/api/generated/`，通过自定义 Mutator 复用统一 `fetch` Client。

生成代码必须满足：

- 不手工修改；通过重新生成覆盖
- 不直接读取 token 或浏览器存储
- 不在生成目录实现业务 Query Key、Toast 或页面跳转
- 由 Feature API 层包装为业务查询和 Mutation
- CI 能检测契约生成物是否过期

如果后端契约无法描述某些运行时不变量，在消费边界补充 Zod 校验；不要为所有内部响应无差别执行重复校验。

### 7.3 TanStack Query

所有服务端数据默认由 TanStack Query 管理。Feature 负责定义 Query Key、Query Option、Mutation、缓存失效和必要的乐观更新；组件不得自行维护第二份远端数据副本。

全局默认值保持保守。重试次数、`staleTime`、垃圾回收和窗口聚焦刷新按数据性质调整，不把同一参数机械复制到所有查询。认证失败由 API Client 处理，不使用 Query 的通用重试制造刷新风暴。

### 7.4 客户端 Store

只有出现以下状态时才引入 Pinia：

- 跨多个无直接父子关系的页面共享
- 不属于服务端缓存
- 不适合表达为 URL
- 生命周期长于单个页面

主题、导航栏状态、草稿元数据等可能符合条件；用户资料、任务列表和权限集合通常属于 Query 数据。Store 默认不持久化，确需持久化时通过 `lib/storage/` 定义版本、迁移和清理策略。

## 8. 表单与运行时校验

Zod 是统一 Schema 工具，用于：

- 环境变量
- 路由参数与查询参数
- 表单输入
- 本地持久化数据恢复
- 不可信第三方响应

简单表单优先使用框架原生受控状态、原生表单语义和 Zod，不因只有两个字段就引入完整表单库。出现动态字段、数组、复杂联动、跨步骤状态或大量字段错误时，使用 vee-validate。

前端校验用于即时反馈，不能替代后端校验。服务端字段错误必须映射回对应字段，通用错误进入表单级错误区域；不能只弹 Toast 后丢失错误上下文。

## 9. 样式与组件系统

### 9.1 Tailwind CSS v4

Tailwind CSS v4 使用 CSS-first 配置：

```css
@import 'tailwindcss';

@theme inline {
  --color-brand: var(--brand);
}
```

新项目不创建 `tailwind.config.ts`，除非必须兼容无法迁移的遗留插件。Design Token 通过 `@theme` 和 CSS 自定义属性定义；组件使用语义 Token，不直接散布品牌色值。动态样式使用完整、可静态发现的 Class 映射，不拼接 `bg-${color}-500` 一类运行时类名。

### 9.2 组件系统

Vue 项目使用 Reka UI + Tailwind CSS v4 + Radix Colors，具体组合见《[[Reka UI + Tailwind CSS v4 + Radix Colors 设计系统方案]]》。Reka UI 负责键盘、焦点、ARIA 和受控状态基础，项目组件负责视觉与业务语义。

Reka UI 只提供组件基础能力，完整语义、键盘、焦点、表单和反馈要求见《[[前端交互与可访问性规范]]》。

Vue 不得同时引入 Element Plus 等第二套 Vue 组件系统。若默认方案确实无法满足项目约束，应整体替换并记录 ADR，而不是逐页混搭。

### 9.3 图标、日期与动画

以下能力按需选择：

- 图标：Lucide 的 Vue 适配包
- 日期计算：优先原生 `Intl`；复杂日期运算使用 `date-fns`
- 动画：优先 CSS Transition；只有手势、编排或物理动画才引入专用库

不得为单个格式化函数或简单淡入动画引入大型依赖。

## 10. 测试栈

测试的分层、目录、Mock 和覆盖率规则以《[[前端测试规范]]》为准。技术选型固定为：

- Vitest：单元、组件和页面集成测试执行器
- Testing Library：Vue 的用户行为测试
- MSW：HTTP 边界 Mock
- Storybook + Vitest addon：共享组件的场景、交互和可访问性测试
- Vitest Browser Mode：确实依赖浏览器行为的组件测试
- Playwright：部署应用、真实路由和关键业务流程的 E2E

Browser Mode 与 E2E 都可能使用 Playwright 浏览器能力，但职责不同：前者仍由 Vitest 执行组件测试，后者从部署应用入口验证完整用户流程。不得用 Storybook Story 代替登录、跨页面创建任务或真实后端协作等 E2E。

## 11. 代码质量与 CI

### 11.1 ESLint 与 Prettier

ESLint 使用 Flat Config，并启用：

- TypeScript 类型感知规则
- Vue 官方规则
- `eslint-plugin-vuejs-accessibility`
- TanStack Query 官方 ESLint 规则
- Import 和无用代码检查

Prettier 只负责格式化，ESLint 负责正确性；关闭相互冲突的格式规则，不让两者争夺同一职责。Tailwind Class 排序可以使用官方 Prettier Plugin，但不得让排序改变组件逻辑或掩盖重复 Class。

### 11.2 必须提供的脚本

项目至少提供语义稳定的脚本：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vue-tsc -b && vite build",
    "typecheck": "vue-tsc --noEmit",
    "lint": "eslint .",
    "format": "prettier . --write",
    "test": "vitest",
    "test:run": "vitest run",
    "test:coverage": "vitest run --coverage",
    "test:e2e": "playwright test",
    "storybook": "storybook dev -p 6006",
    "storybook:build": "storybook build"
  }
}
```

实际脚本可以因 Monorepo 或部署平台调整，但 `typecheck`、`lint`、`test:run`、`test:e2e` 和 `build` 的语义不能改变。

### 11.3 CI 基线

每次合并至少验证：

1. Frozen Lockfile 安装
2. API 生成物未过期
3. TypeScript 类型检查
4. ESLint
5. Vitest 普通测试与 Storybook Project
6. Storybook 静态构建
7. 生产构建

Playwright E2E 至少在主分支、发布候选或具备稳定部署环境的合并请求上运行；认证、核心写操作和高风险回归流程不得只依赖人工验证。

## 12. 按需能力

| 能力 | 默认选择 | 何时引入 |
| --- | --- | --- |
| 国际化 | Vue I18n | 产品明确支持多语言时 |
| PWA | `vite-plugin-pwa` | 明确需要离线、安装或推送时 |
| 原生容器 | Capacitor | 需要 App Store / 系统 API 且 Web 能力不足时 |
| 错误监控 | Sentry 或部署平台现有方案 | 生产环境需要前端错误与性能追踪时 |
| WebSocket | 浏览器 WebSocket + Feature 封装 | 产品确有实时双向事件时 |
| 可视化 | 按图表需求单独评估 | 出现真实图表和交互需求时 |
| 大文件上传 | 专用上传协议与 Client | 需要分片、续传或直传对象存储时 |

引入按需能力前，先确认浏览器原生 API 和现有栈无法以可维护方式完成。新依赖必须说明 Bundle 影响、维护状态、许可证、SSR/浏览器兼容性和测试方法。

## 13. 非默认方案

以下技术不是被永久禁止，而是不作为普通 SPA 的默认答案：

- Next.js、Nuxt、Remix 等全栈或 SSR 框架
- Vuex 等额外 Store
- Axios、GraphQL Client 或 RPC Client
- CSS-in-JS 和第二套 Utility CSS
- Vue 中的 Element Plus 等第二套组件系统
- 自动文件路由
- 微前端
- Service Worker 与离线缓存
- Monorepo 编排工具
- 全局 Event Bus

只有明确的产品或组织约束成立时才评估它们，并同时调整架构、部署、安全和测试规范。不要把局部需求包装成全项目基础设施。

## 14. 新项目检查清单

### 基线

- [ ] Node、pnpm 和 `packageManager` 已锁定？
- [ ] 只提交 `pnpm-lock.yaml`？
- [ ] TypeScript `strict` 与 Vite ESM 配置已启用？
- [ ] 页面统一放在 `src/pages/`？

### 数据与 API

- [ ] 所有请求经过唯一 `lib/api/client.ts`？
- [ ] Orval 生成物只放在 `lib/api/generated/` 且可重复生成？
- [ ] TanStack Query 是服务端数据唯一权威来源？
- [ ] Pinia 只在出现真实跨页面客户端状态后引入？
- [ ] token、认证刷新和 `401` 重放遵循认证集成规范？

### UI 与测试

- [ ] Tailwind CSS v4 使用 CSS-first 配置和语义 Token？
- [ ] 使用 Reka UI，未混入第二套组件系统？
- [ ] Vitest、Testing Library、MSW 和 Storybook 已建立？
- [ ] Playwright 已覆盖至少一条关键部署流程？
- [ ] CI 能完成类型检查、Lint、测试、Storybook 与生产构建？
